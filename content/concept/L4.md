# L4: Qdrant Vector Search - Schema & Implementation

This document defines the complete schema, algorithms, and configuration for the L4 (Qdrant) semantic vector search tier in the RecoverySky memory system.

## Overview

L4 is the semantic search layer of the multi-tier memory architecture. It stores message embeddings in Qdrant and enables similarity-based retrieval across a user's entire conversation history.

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Memory Tier Architecture                          │
├─────────────────────────────────────────────────────────────────────┤
│  L1 (Redis)     - Session cache        - <10ms     - 4hr TTL        │
│  L2 (PostgreSQL)- Full history         - 10-50ms   - Persistent     │
│  L3 (Neo4j)     - Knowledge graph      - 10-30ms   - MCP-compatible │
│  L4 (Qdrant)    - Semantic search ◄──  - 5-20ms    - 90 day window  │
└─────────────────────────────────────────────────────────────────────┘
```

### Point ID Generation

Qdrant requires UUID or numeric IDs. We generate deterministic UUIDs from message IDs using SHA-256:

```typescript
// packages/memory/src/qdrant/schema.ts
export function messageIdToPointId(messageId: string): string {
  const hash = createHash('sha256').update(messageId).digest('hex')
  // Format as UUID: 8-4-4-4-12
  return [
    hash.slice(0, 8),
    hash.slice(8, 12),
    hash.slice(12, 16),
    hash.slice(16, 20),
    hash.slice(20, 32),
  ].join('-')
}
```

**Benefits:**
- Deterministic: Same message ID always produces same point ID
- Idempotent: Re-indexing doesn't create duplicates
- Collision-resistant: SHA-256 provides ~128 bits of collision resistance

## Search Algorithm

### Similarity Metric: Cosine Distance

Cosine similarity measures the angle between two vectors, normalized to [-1, 1]:

```
cos(θ) = (A · B) / (||A|| × ||B||)
```

For normalized vectors (which OpenAI embeddings are):
- `1.0` = Identical direction (maximum similarity)
- `0.0` = Orthogonal (no correlation)
- `-1.0` = Opposite direction (maximum dissimilarity)

### In-Memory Implementation

The `InMemoryVectorStore` provides a reference implementation:

```typescript
// packages/memory/src/stubs/InMemoryVectorStore.ts
private cosineSimilarity(a: number[], b: number[]): number {
  if (a.length !== b.length) return 0

  let dotProduct = 0
  let normA = 0
  let normB = 0

  for (let i = 0; i < a.length; i++) {
    dotProduct += a[i] * b[i]
    normA += a[i] * a[i]
    normB += b[i] * b[i]
  }

  if (normA === 0 || normB === 0) return 0
  return dotProduct / (Math.sqrt(normA) * Math.sqrt(normB))
}
```

### Filter Construction

The search method builds Qdrant filter conditions:

```typescript
// packages/memory/src/stores/QdrantVectorStore.ts
// Must conditions (all required)
const mustConditions = [
  { key: 'userId', match: { value: userId } },        // User filter
  { key: 'timestamp', range: { gte: cutoffTimestamp } } // Time filter
]

// If conversation specified
if (conversationId) {
  mustConditions.push({
    key: 'conversationId',
    match: { value: conversationId }
  })
}

// Required topics (any match)
if (requiredTopics.length > 0) {
  mustConditions.push({
    key: 'topics',
    match: { any: requiredTopics }
  })
}

// Must not conditions (exclusions)
const mustNotConditions = excludeCrisisLevels.map(level => ({
  key: 'crisisLevel',
  match: { value: level }
}))
```

### Error Mapping

Qdrant errors are mapped to domain error types:

```typescript
function mapQdrantError(error: unknown): StoreError {
  // Connection errors
  if (code === 'ECONNREFUSED' || code === 'ENOTFOUND') {
    return { kind: 'ConnectionError', message: '...' }
  }

  // Timeout errors
  if (code === 'ETIMEDOUT' || message.includes('timeout')) {
    return { kind: 'TimeoutError', message: '...' }
  }

  // Validation errors (400)
  if (status === 400) {
    return { kind: 'ValidationError', message: '...' }
  }

  // Not found (404)
  if (status === 404) {
    return { kind: 'NotFoundError', message: '...' }
  }

  return { kind: 'UnexpectedError', message: '...' }
}
```

## Pruning Strategy

Old vectors are removed to control storage costs:

```typescript
async prune(olderThanDays: number, ctx: TraceContext): Promise<Result<number, StoreError>> {
  const cutoffTimestamp = Date.now() - olderThanDays * 24 * 60 * 60 * 1000

  // Scroll through old points
  const pointIdsToDelete: string[] = []
  let offset: string | number | undefined = undefined

  do {
    const scrollResult = await this.client.scroll(this.collectionName, {
      filter: {
        must: [{
          key: 'timestamp',
          range: { lt: cutoffTimestamp }
        }]
      },
      limit: this.batchSize,
      offset,
      with_payload: false,
      with_vector: false,
    })

    for (const point of scrollResult.points) {
      pointIdsToDelete.push(point.id as string)
    }

    offset = scrollResult.next_page_offset ?? undefined
  } while (offset !== undefined)

  // Delete in batches
  for (let i = 0; i < pointIdsToDelete.length; i += this.batchSize) {
    const batch = pointIdsToDelete.slice(i, i + this.batchSize)
    await this.client.delete(this.collectionName, {
      wait: true,
      points: batch,
    })
  }

  return ok(pointIdsToDelete.length)
}
```

**Recommended schedule:** Run daily to prune vectors older than 90 days.

## Best Practices

1. **Always scope searches by userId** to maintain data isolation
2. **Use appropriate scoreThreshold** (0.7 is good default, lower for broader recall)
3. **Set reasonable daysBack** (90 days balances relevance and storage)
4. **Batch indexing** for bulk imports (100 messages per batch)
5. **Run pruning** regularly to control storage costs
6. **Handle errors gracefully** - L4 is non-critical, system can function without it
